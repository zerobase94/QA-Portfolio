My Strength

문서를 읽고
TC로 만드는 과정

문서 분석에서 가장 중요하게 보는 것은 “무엇을 테스트할까?”보다 “이 Requirement가 실제로 어떤 조건에서 참이어야 하고, 어떤 조건에서 달라져야 하는가?”입니다.

01 · DOCUMENT ANALYSIS

Requirement를 기능 단위로 분해

SyRS와 Specification을 읽고 단순 문장 단위가 아니라 기능, 입력값, 상태, 선행조건, 예외조건으로 나누어 이해합니다.

확인 어떤 조건에서 기능이 동작하는가
분리 정상 / 비정상 / 상태 변화 / 경계 조건
목적 문서 내용이 빠짐없이 검증 대상으로 연결되는지 확인
02 · TEST CONDITION

문장을 검증 조건으로 변환

Requirement를 그대로 TC 제목으로 옮기지 않고, 실제로 Pass/Fail을 판단할 수 있도록 Test Condition으로 변환합니다.

Precondition 검증 시작 전 시스템 상태 정의
Input Signal / Value / User Action 등 입력 조건 정의
Expected 결과를 관찰 가능한 형태로 명확화
03 · COVERAGE REVIEW

기존 TC와 Requirement 비교

기존 Test Case가 있더라도 그대로 신뢰하지 않고 Requirement와 다시 비교해 누락된 조건이 있는지 확인합니다.

실제 사례 Volkswagen Security TC 재검토
수행 SyRS와 기존 TC의 연결 관계를 다시 확인
결과 12건이던 Security TC를 49건으로 확대
04 · REVIEW & STANDARD

다른 사람이 수행해도 같은 결과

좋은 TC는 작성자만 이해하는 문서가 아니라, 다른 검증자가 수행해도 동일한 조건과 판단 기준으로 테스트할 수 있어야 한다고 생각합니다.

HKMC ccIC 팀 단위 TC Review 운영
검토 절차의 모호함 / Expected Result / Requirement 누락
공유 좋은 TC 사례와 작성 기준을 팀 표준으로 공유

Document → Test Case 사고 흐름

1. Read

SyRS / Specification에서 기능 목적과 조건을 파악합니다.

2. Decompose

입력값, 상태, Precondition, 예외조건, Timing 요소로 분해합니다.

3. Design

각 조건을 Test Procedure와 Expected Result가 있는 Test Case로 설계합니다.

4. Review

Requirement 누락과 중복, 모호한 판단 기준을 검토하고 보완합니다.

How I Work

문서에서 TC까지
업무 방식

Requirement를 해석하고 Test Condition을 만들고, 수행 가능한 Test Case로 정리한 뒤 Issue와 Regression까지 연결하는 실제 업무 흐름입니다.

1. 문서 분석

Requirement에서 기능 조건과 검증 포인트 추출

2. Test Case 설계

조건을 절차·입력·Expected Result로 구조화

3. 검증 후 반영

Issue와 Spec 변경을 Re-test / Regression에 연결

1. Requirement / Specification 분석

읽는 관점

기능 목적, 동작 조건, 상태 변화, 입력 범위, 예외 조건을 문서에서 분리해 확인합니다.

확인 결과

각 Requirement가 어떤 Test Condition으로 검증되어야 하는지 연결 관계를 정리합니다.

2. Test Condition → Test Case

설계

Precondition, Input, Procedure, Expected Result를 구분하고 정상·비정상·상태·경계 조건을 TC로 만듭니다.

Review

다른 검증자가 수행해도 같은 결과를 얻을 수 있는지, Requirement가 누락되지 않았는지 확인합니다.

3. 결과를 다시 Test Case에 반영

Issue

재현 조건과 환경을 정리해 JIRA에 등록하고 수정 상태를 관리합니다.

Feedback

수정 후 Re-test / Regression을 수행하고, 새로 확인된 Risk와 Spec 변경을 이후 Test Case 기준에 반영합니다.
